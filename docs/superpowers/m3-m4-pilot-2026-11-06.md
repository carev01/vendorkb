# M3/M4 pilot: claims, taxonomy v1, capability table (2026-11-06)

Implements `specs/2026-11-06-m3-m4-claims-taxonomy-design.md` (plan
`plans/2026-11-06-m3-m4-claims-taxonomy.md`) on production data.

## What was built

- **Claim extraction** (`src/vendorkb/claims/`).
  - Claude Haiku 5.5 with strict JSON-schema output and effort "low".
  - Two backends: the Anthropic SDK (Messages and Batches API) and any OpenAI-compatible
    endpoint.
  - A verbatim evidence gate: normalized substring, then punctuation-insensitive substring, then
    fuzzy matching (partial ratio ≥ 90). The fuzzy step requires every word, every number and
    every negation of the quote to appear in the matched span, and rejects a negation the quote
    drops. Quotes need at least 3 words or 15 characters.
  - `evidence_quote` stores the chunk's own text.
  - A spend ledger that never cascade-deletes, a run lock, batch resume, an attempt cap and a
    budget cap.
- **Taxonomy** (`src/vendorkb/taxonomy/`).
  - Bounded agglomerative clustering: strings seen 2 or more times or from 2 or more vendors,
    capped at 15,000. The rest go to a long-tail file.
  - Haiku proposals with strict JSON. A YAML loader with a hashed version.
  - The mapper: exact alias, then embedding nearest neighbour, else unmapped.
  - `capabilities build|query`.

## Run (production, pilot of 21,382 chunks)

- **Model route.** Haiku 5.5 ran through OpenRouter (`anthropic/claude-haiku-5.5`). The
  Anthropic credential in `.env` is an `sk-ant-usr` token the API rejects (401). The Anthropic
  Batches path is in the code, untested live.
- **Sample.**
  - (a) 3,000 chunks from each pilot vendor (Commvault, Cohesity, Rubrik, Druva, AvePoint),
    stratified by product.
  - (b) every chunk of every document cited in the 23 enumeration questions' `expected_vendors`.
  - (c) the top-5 hybrid candidates per vendor for each enumeration question.
  - Parts b and c ran first; a filled the budget.
- **Extraction.** 20,828 chunks done and 335 errored (mostly output cut off at max_tokens 2000,
  in claim-dense chunks; not re-run). That gave **75,128 accepted claims** from all 43 vendors.
  - The **gate pass rate is 99.4%**, against a target of ≥ 90%. Most rejections were quotes that
    were too short.
  - Cost: **$8.98**.
- **Claim precision** (100 random claims, 2 Opus subagents): **86/100**. **Target ≥ 95%: not
  met.** No claim was hallucinated. The errors:

  | Error | Count | What went wrong |
  |---|---|---|
  | wrong_support | 7 | "partial" used for prerequisites or off-by-default features |
  | not_a_capability | 5 | procedures or known issues extracted as capabilities |
  | wrong_target | 1 | |
  | other | 1 | |

  Both main error classes are prompt fixes for `claims-v2`: define "partial" narrowly, and
  exclude procedures and known issues.
- **Taxonomy proposals.**
  - Clustering at threshold 0.12 (0.25 and 0.18 lumped distinct features into "backup").
  - Features: 3,822 clusters; proposals stopped at the budget after 2,213 of them, giving 2,071
    entries.
  - Targets: 2,360 clusters; 980 proposed, giving 969 entries.
  - Cost: $0.57, largest clusters first.
- **Mapping** (nearest-neighbour threshold 0.80, uncalibrated): 93% of claims map to a feature
  (38% by alias, 55% by nearest neighbour). Targets map 58,620 times, and 14,729 claims have no
  target.
- **Re-gate.** The final review found exact matches that started inside a word ("supported" inside
  "unsupported"). After the gate fix, `vendorkb claims regate` moved 243 claims (0.3%) to
  `rejected_claims` and re-derived the span of 655. **74,885 claims** remain.
- **Capability table.** 69,777 rows after the re-gate, covering 43 vendors, 2,064 features and
  882 targets. The M4 numbers below were re-measured after the re-gate and are unchanged.
  - Support values: 80% supported, 11% partial, 6.5% not_supported, 2% unclear.

## M4 measurement (23 labelled enumeration questions)

Each question resolves to features and targets from its `key_terms` (exact alias, else nearest
neighbour at cosine ≥ 0.85). The table's answer is every vendor with a supported or partial row
for those features or targets, target descendants included.

| Source | Vendor recall | Vendor precision | Vendors found per question |
|---|---|---|---|
| Capability table | 0.911 (calibration 0.838 / holdout 0.978) | 0.828 | 19.9 |
| Table, excluding vendors found only via retrieval candidates | 0.895 | 0.900 | 18.0 |
| Retrieval enumeration (FTS 0.25, floor 0.54) | 0.952 | 0.877 | 19.7 |
| **Table ∪ retrieval** | **0.990** | 0.788 | 22.7 |

**Mapper calibration** (80 nearest-neighbour feature mappings, 20 per cosine band, judged by an
Opus subagent):

| Cosine band | Correct |
|---|---|
| 0.80–0.83 | 3/20 |
| 0.83–0.86 | 7/20 |
| 0.86–0.90 | 11/20 |
| ≥ 0.90 | 12/20 |

Embedding nearest neighbour is **not reliable** at any threshold for fine-grained features. It
needs the LLM adjudication step from DESIGN.md §5.4. With **alias-only** mappings (no nearest
neighbour):

| Source (alias-only table) | Vendor recall | Vendor precision | Found per question |
|---|---|---|---|
| Capability table | 0.846 (calibration 0.722 / holdout 0.958) | **0.913** | 16.6 |
| **Table ∪ retrieval** | **0.984** | **0.842** | 21.2 |

The union with the alias-only table is the best trade-off measured. It gains 3 points of recall
over retrieval alone (0.952) for 3.5 points of precision; the answer step's per-vendor citation
check filters further.

Resolving from the question text too, at cosine 0.75, gives table 0.954 / 0.728 and union
0.991 / 0.705: more recall, lower precision.

**Caveats**
- **Recall is partly circular.** Pilot part (b) extracted every chunk of the documents the labels
  cite, so table recall is optimistic for vendors and documents outside the pilot.
- **Nothing is calibrated yet.** The mapper threshold, the clustering threshold and the
  resolution threshold are all uncalibrated.
- **Precision is the table's weak side.** Broad features pull in vendors, for example "legal
  hold" resolving to "alternate location restore".

**Takeaway.** The table finds vendors that retrieval misses, and retrieval finds ones the table
misses. Together they reach 0.99 recall. The obvious integration is to add table vendors to the
enumeration candidates. The answer step's line check, which keeps a vendor only with its own
cited chunk, then holds precision.

## Taxonomy review

`taxonomy/taxonomy.yaml` v1 is on the draft PR (branch `taxonomy-v1`) for review. Nothing is
final until it is approved. It has 2,071 features and 969 targets. Known issues:
- **Duplicate-looking targets** with different parents, for example `platforms.kubernetes` and
  `kubernetes.cluster`.
- **Generic targets** such as `backup.data`.
- **Many Management-category features**: 729.

The long tail (`taxonomy/long_tail.yaml`) is reference material, not part of the reviewed
taxonomy.
